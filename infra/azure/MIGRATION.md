# Moving to a new Azure subscription

For when the Azure for Students offer ends and you start again on a new account.
Written to be followed a year from now by someone who has forgotten the details —
which is to say, by you.

Budget **40 minutes**, most of it waiting for tenant creation.

---

## Why this is a short document

Almost nothing has to move. Two design decisions did the work up front:

- **Traces are content-addressed.** A blob's name is the SHA-256 of the inputs
  that produced it, so nothing is uniquely valuable — anything lost is
  regenerated by running the code again. There is no database, no schema, no
  migration.
- **The Azure integration is optional at runtime.** The app runs identically
  with it switched off, so the gap between tearing down the old subscription
  and finishing the new one is a *degradation*, not an outage. You can take a
  week over this if you want.

User accounts do not move either, but not because of Azure -- they never lived
there. They are a file in the backend's data directory, so they survive this
migration untouched and are instead lost on any redeploy that replaces the
container filesystem. If that ever matters, it is the point at which the
`UserStore` interface gets a Postgres implementation.

## Before the old account expires

**Find your deadline.** [microsoftazuresponsorships.com/balance](https://www.microsoftazuresponsorships.com/balance)
shows remaining credit and the expiry date. Once the subscription is disabled,
getting anything back out of it needs a support request — so do this while it is
still alive.

**Optionally, keep the old traces.** Only worth it if you have share links in
circulation you would rather not break. Skip it otherwise; the storage is a
cache.

```bash
# From the OLD subscription. The destination folder must already exist.
mkdir -p ./trace-backup
az storage blob download-batch \
  --source traces \
  --destination ./trace-backup \
  --connection-string "$OLD_CONNECTION_STRING"
```

Restoring into the new account is covered in step 3.

## 1. Create the new account

Go to [azure.microsoft.com/free](https://azure.microsoft.com/free) and sign up
with a **personal** Microsoft account — not the university one, which is about to
stop being yours.

Two things to expect:

- **A card is required** for identity verification. It is not charged unless you
  explicitly move to pay-as-you-go, but it must be a real card.
- **One free trial per person.** If you have used one before, you will land on
  pay-as-you-go instead. That is fine for this project: everything below stays
  inside free tiers or costs cents, and the budget alert in step 2 is your
  backstop.

> **The silver lining.** A personal account is not inside your university's
> directory, so the permission restrictions that come with a managed student
> tenant do not apply. Nothing here needs them any more — storage is the only
> resource left — but it does mean a personal subscription is the simpler place
> to run this from.

Then point the CLI at it:

```bash
az login
az account show --query "{subscription:name, tenant:tenantId, user:user.name}" -o table
```

Confirm `user` is the new personal account before continuing. Provisioning into
the wrong subscription is the easiest mistake here and the most annoying to
unpick.

## 2. Guard the spend first

Do this **before** creating anything, so there is never a window without it.

```bash
# macOS. On Linux the end date is: $(date -d '+1 year' +%Y-%m-01)
az consumption budget create --budget-name visualizer-guard \
  --amount 1 --time-grain monthly --category cost \
  --start-date "$(date +%Y-%m-01)" --end-date "$(date -v+1y +%Y-%m-01)"
```

The enum values are lowercase (`monthly`, `cost`) and the CLI rejects
`Monthly`/`Cost` outright. `az consumption` is also still flagged preview, so if
it has moved on by the time you read this, set the budget in **Cost Management →
Budgets** in the portal instead — the value matters, the mechanism does not.

`$1/month` is deliberately absurd for a workload that should cost cents. It is a
smoke alarm, not a limit — you want it to go off at the first sign of something
unexpected, rather than discovering a mistake on a monthly statement.

## 3. Provision storage

```bash
cd infra/azure
./provision.sh storage
```

That creates the resource group, a `Standard_LRS` storage account with public
blob access disabled, the container, and a 90-day lifecycle rule — then prints
the two environment variables. It is idempotent, so re-run it freely.

Tune it with environment variables if you need to:

```bash
AZ_LOCATION=westeurope AZ_RETENTION_DAYS=30 ./provision.sh storage
```

**If you backed up the old traces**, restore them now so existing links keep
resolving. The blob names are content hashes, so this is a straight copy with no
translation:

```bash
az storage blob upload-batch \
  --source ./trace-backup \
  --destination traces \
  --connection-string "$NEW_CONNECTION_STRING"
```

### Verify before moving on

```bash
# From the repo root, with the new connection string in .env
docker compose up --build -d
docker compose logs backend | grep "Trace archive"
```

Expect `Trace archive enabled: Azure Blob Storage container 'traces'.`

Then the test that actually proves it, because it is the one that fails without
Azure:

1. Run a snippet in the UI and click **Share**.
2. `docker compose restart backend` — this empties the in-memory cache.
3. Open the shared link. It still replays, from the blob.

## 4. Update the deployment

One variable changes. In the Render dashboard (or `.env` locally):

| Variable | Where it comes from |
|---|---|
| `AZURE_STORAGE_CONNECTION_STRING` | step 3 output |

That is the whole migration surface. Accounts are self-hosted and have no Azure
resource behind them, so nothing about sign-in moves with the subscription --
`VISUALIZER_AUTH_SECRET` belongs to the deployment, not to Azure, and must be
left exactly as it is. Changing it signs every user out.

### Verify

```bash
curl -i https://your-app.onrender.com/api/health
# 200, and still public -- the platform health check depends on it

curl -i -X POST https://your-app.onrender.com/api/trace \
  -H 'Content-Type: application/json' \
  -d '{"language":"python","source":"x=1"}'
# 401 -- the API is genuinely closed, not just visually gated
```

Then in a browser: sign in, run a snippet, and press **Share**. The link must
still resolve after a restart, which is the one thing the new storage account
is responsible for.

---

## 5. Decommission the old subscription

Only once step 4 is verified.

```bash
# Signed into the OLD account
az login
./provision.sh teardown
```

Then let the old subscription lapse, or cancel it in the portal.

## Keeping it cheap

The costs here are structural rather than a matter of vigilance, which is why
this section is short:

- **The app is not hosted on Azure.** It stays on Render's free tier. Azure
  provides storage and identity only — the two things that are free or nearly
  free. Moving compute to App Service or Container Apps is what would actually
  cost money, and it would buy nothing this project needs.
- **`Standard_LRS`, not GRS.** Geo-replication for a cache of recomputable data
  is paying for durability the data does not need.
- **Content-addressing makes writes idempotent.** Uploads are create-only
  (`If-None-Match: *`), so re-running the same snippet is not a billed write.
- **A lifecycle rule expires blobs at 90 days**, so storage cannot creep.
- **The rate limiter covers `GET /api/trace/{id}`**, the one endpoint that bills
  a storage transaction on a cache miss.

Expected steady state: **cents per month**, dominated by a few megabytes of JSON.

### If you would rather not maintain it at all

Perfectly reasonable, and the app is built for it. Clear
`AZURE_STORAGE_CONNECTION_STRING` and redeploy — the in-memory cache comes back
and nothing errors. Sign-in is unaffected: it has no Azure dependency to lose.

> This used to carry a warning that switching Azure off in the wrong order left
> the app bricked but looking healthy, because a dead tenant 401ed every
> `/api/**` call while `/api/health` kept passing. That failure mode is gone
> with the tenant. A dead archive degrades to a cache miss and the run still
> succeeds, which is the only Azure failure left.

## Troubleshooting

Setup problems that are not migration-specific are covered in
[README.md](README.md#troubleshooting).

Migration-specific ones:

**`az` commands hitting the old subscription.** `az account show`. Switch with
`az account set --subscription <id>`, and remember that tenant-scoped commands
(`az ad ...`) follow `az login --tenant`, not the subscription.

**`Insufficient privileges` from `provision.sh app`.** You are signed into a
subscription rather than the external tenant. Re-run
`az login --tenant <tenant-id> --allow-no-subscriptions`.

**Old share links 404 after migrating.** Expected unless you copied the blobs.
The ids are still valid — re-running the same code regenerates the identical
hash, and the link starts working again.

**Storage account name already taken.** The name is part of a public hostname
and so globally unique. Re-run; the default includes a random suffix. Pass
`AZ_STORAGE_ACCOUNT=<name>` to pin one.

**`RequestDisallowedByAzure ... best available regions`.** Some subscriptions
(Azure for Students among them) are policy-restricted to a subset of regions,
and the default `eastus` may not be in it. Re-run with an allowed one:

```bash
AZ_LOCATION=centralindia ./provision.sh storage
```

To see the list rather than guessing:

```bash
az policy assignment list \
  --query "[].{name:displayName, allowed:parameters.listOfAllowedLocations.value}" -o json
```

Note that the *resource group* is not region-restricted the same way, so group
creation succeeding tells you nothing about whether the storage account will.

**`SubscriptionNotFound` when the subscription plainly exists** — `az account
list --refresh` shows it Enabled, and the resource group was created moments
earlier. The resource provider is unregistered, not the subscription missing:
creating a resource group goes through `Microsoft.Resources`, which is always
registered, while the storage account goes through `Microsoft.Storage`, which on
a new subscription may never have been. `provision.sh` now registers it, but by
hand it is:

```bash
az provider show --namespace Microsoft.Storage --query registrationState -o tsv
az provider register --namespace Microsoft.Storage --wait
```

**`az consumption budget create` returns 400 "use filter interface with
2019-05-01-preview".** The preview command does not match the current API on
some subscription types. Create the budget under **Cost Management → Budgets** in
the portal instead — the $1 alarm is what matters, not how it was made.
